# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- Датасет: S12-hw-dataset.csv, прогнозировалась колонка target (временной ряд с часовой частотой).
- Разбиение: train / validation / test организованы строго по времени (70% / 15% / 15%).
- Подходы: Сравнены наивный базлайн (B1), скользящее среднее (B2), Ridge-регрессия на лагах (B3) и рекуррентная сеть GRU (R1).
- Итог: Лучшим подходом оказалась модель GRU (R1), так как она показала наименьшую ошибку на валидации по сравнению с линейными методами благодаря способности улавливать нелинейные зависимости временного ряда.

## 2. Среда и воспроизводимость

- Python: 3.14.2
- pandas / numpy / scikit-learn: стандартные версии окружения курса
- torch: стандартная версия окружения курса
- Устройство (CPU/GPU): CPU
- Seed: 42 (зафиксирован для random, numpy, torch)
- Как запустить: открыть HW12.ipynb и выполнить Run All.

## 3. Данные и постановка задачи

- Датасет: S12-hw-dataset.csv
- Целевая колонка: target
- Частота временного ряда: Часовая (24 наблюдения в сутки)
- Горизонт прогноза: 1 шаг (next value prediction)
- Размер датасета: 4320 наблюдений
- Диапазон дат: 2025-01-01 00:00:00 — 2025-06-29 23:00:00
- Есть ли дополнительные внешние признаки: Нет, только дата и таргет (остальные признаки сконструированы)
- Комментарий: Данные представляют собой непрерывный часовой ряд без пропусков. Наблюдается выраженная суточная сезонность (что обосновывает использование лагов 1, 7, 14) и возможный тренд. Отсутствие пропусков упрощает предобработку, однако нестационарность ряда требует аккуратного построения признаков и масштабирования.


## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- Как именно выполнен train / validation / test: Последовательное разбиение через iloc без перемешивания.
- Какие доли или интервалы использовались: 70% train (3024 наблюдения), 15% validation (648 наблюдений), 15% test (648 наблюдений).
- Почему random split здесь некорректен: При случайном разбиении модель обучается на данных из «будущего» относительно валидации, что приводит к утечке информации и некорректной оценке качества (занижение ошибки). Временная зависимость нарушается.


### 4.2. Признаки для baseline-моделей

- Какие лаги использовались: lag_1, lag_7, lag_14.
- Какие rolling-признаки использовались: rolling_mean_7, rolling_std_7 (окно 7, сдвиг 1).
- Какие календарные признаки использовались: day_of_week (день недели).
- Как обрабатывались пропуски после построения лагов/rolling: Строки с NaN удалены через dropna().
- Использовалось ли масштабирование и где именно оно обучалось: Да, StandardScaler. Обучался (fit) только на train, применялся (transform) на train, val, test.


## 5. Модели и эксперименты (B1, B2, B3, R1)

- B1 (naive-last): Прогноз равен последнему известному значению (lag_1).
- B2 (moving-average): Прогноз равен скользящему среднему за 7 шагов.
- B3 (ridge-lag-features): Линейная регрессия Ridge на всех сконструированных признаках.
- R1 (gru-forecast): Рекуррентная сеть GRU на оконном представлении ряда (window_size=14).

Дополнительно:

- Основная метрика выбора лучшей модели: MAE (на валидации).
- Дополнительные метрики: RMSE, MAPE.
- window_size для GRU: 14.
- Batch size: 32.
- Максимальное число эпох: 10.
- Optimizer: Adam.
- Learning rate: 1e-3.
- Как сохранялась лучшая модель: Сохранение state_dict при улучшении val_loss (artifacts/best_gru.pt).

## 7. Анализ

Наивный baseline (B1) оказался surprisingly сильным, что характерно для рядов с высокой автокорреляцией первого порядка (значение сильно зависит от предыдущего). Moving Average (B2) показал худший результат из-за сглаживания полезных всплесков. Ridge (B3) на признаках сработала хуже простого лага, возможно, из-за мультиколлинеарности лаговых признаков или нелинейности зависимостей, которую линейная модель не уловила. GRU помогла снизить ошибку, так как архитектура способна запоминать последовательности внутри окна лучше, чем статичные признаки. В данных заметна сезонность (суточная), что отражается в эффективности лагов 7 и 14. Утечки данных могли появиться при неправильном расчете rolling-признаков (без сдвига) или при масштабировании на всем датасете сразу. Выбор по validation, а не по test, принципиален, чтобы не «подогнать» модель под тестовые данные и оценить обобщающую способность. Наиболее показательными оказались ошибки на пиках ряда, где линейные модели сглаживают прогноз, а GRU пытается повторить форму.

## 8. Итоговый вывод

В качестве базового подхода для такой задачи я бы взял GRU, так как она показала наилучшее качество на валидации.
Простого baseline на признаках (Ridge) достаточно, если данные сильно линейны и требуется интерпретируемость или высокая скорость работы.
Переходить к GRU/нейросетям имеет смысл, когда важны нелинейные зависимости и контекст последовательности, а вычислительные ресурсы позволяют обучать модель.
Главное, что я понял про корректную валидацию временных рядов: никогда не перемешивать данные, всегда соблюдать хронологический порядок при разбиении и построении признаков, чтобы не допустить утечки будущего в прошлое.
